# Free local QA environment

Quantum HRMS can keep the hosted Supabase project on the Free plan while all destructive, authenticated, and active-security tests run against a disposable local Supabase stack. The local stack uses Colima, Docker CLI, and the Supabase CLI; it never consumes a hosted project slot.

## One-time macOS prerequisites

```bash
brew install colima docker docker-compose
colima start --cpu 4 --memory 6 --disk 40
npm install
```

Colima can be stopped when QA is finished with `colima stop`. Starting it again preserves the local Supabase Docker volumes unless the project is explicitly reset or stopped with data deletion.

## Complete local security gate

```bash
npm run test:qa:local
```

This command:

1. Starts the local Supabase services and applies every migration.
2. Runs eight pgTAP assertions covering the 24 HRMS tables, RLS policies, protected workflow functions, fictional profiles, and Realtime publication.
3. Creates or rotates `admin@quantum.test` and `employee@quantum.test` with separate random passwords.
4. Keeps those passwords only in the running Node process; they are not printed or written to a file.
5. Starts the local React application with localhost-only Supabase keys.
6. Runs real Playwright login, portal-access, cross-role rejection, profile, navigation, and sign-out journeys.
7. Stops the temporary Vite process after the tests.

The runner refuses any Supabase API URL that is not `127.0.0.1`, `localhost`, or `::1`. The Playwright preflight also requires the local environment marker and project identity before authentication starts.

## Useful commands

```bash
npm run local:supabase:start
npm run local:supabase:reset
npm run test:db:local
npm run test:e2e:local
npm run local:app
npm run local:supabase:stop
```

- Local API: `http://127.0.0.1:54321`
- Supabase Studio: `http://127.0.0.1:54323`
- Local email inbox: `http://127.0.0.1:54324`
- Local React application: `http://127.0.0.1:4175`

`local:supabase:reset` always includes `--local`. Do not add `--linked` to a reset or test command.

## Local OWASP ZAP active scan

Start the local application in one terminal:

```bash
npm run local:app
```

Then run the authorized active scan in another terminal:

```bash
ZAP_STAGING_TARGET="http://host.docker.internal:4175" \
  ./security/zap/run-active-staging.sh
```

`host.docker.internal` is the container-only address for the local Vite server. It is not a public website. The script permits only that exact local target or the already authorized Netlify preview hostname and continues to reject `quantumnhr.com` for active scanning.

Generated ZAP reports remain ignored under `security/zap/reports/`. Manually review medium/high findings before importing a sanitized JSON report into any demonstration Security Center.

## Data boundary

- All seeded profiles and HR records are fictional.
- Local Auth users never exist in hosted Supabase.
- Local service-role and publishable keys are generated by the CLI and never committed.
- No Resend messages are sent; local Supabase email is captured by the local inbox.
- The linked production project is not pushed, reset, branched, or modified by this workflow.
- Active ZAP scanning stays local; the public website remains passive-baseline only.
